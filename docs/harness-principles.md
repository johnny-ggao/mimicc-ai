# Harness 工程十二原则

一份修订过的清单。起点是三份外部材料——「五大 Harness 原则」「四大失败模式与对策」「背压模型」——按本仓库的实际伤疤修订、合并、补全。原五条只覆盖仓库一侧，窗口内侧整个缺失；四大失败模式其实是同一条原则的四个现场，拎出来成为原则 4；背压模型订正之后成为贯穿全篇的前馈／后馈横切轴。每条原则尽量写明自己的失败模式和边界，而不是只说正面。

## 横切轴：前馈与后馈

十二条原则可以沿一条控制论的轴重新切开：**前馈**——误差发生之前，凭对过程的建模塑造输入；**后馈**——量测输出，把误差信号送回去修正。这条轴来自对「背压模型」（上游背压／下游背压）的订正：backpressure 在原产地 reactive streams 专指下游逆着数据流向上游发的限流信号，方向性是这个词的全部内容。按严格读法「上游背压」名不副实——在执行前施加的约束不是背压，就是前馈；只有下游那一半是真背压。

三条控制论推论：

1. **前馈只能挡住建了模的扰动。** 上游规则是对「agent 惯于怎么错」的建模，模型没覆盖的错法一律放行——前馈永远需要后馈兜底，单独的上游约束是漏的。
2. **后馈的质量上限是传感器的质量。** 传感器没校准，自我修复收敛到的是「骗过坏传感器」而不是「正确」——比没有反馈更毒，因为它高速地错（原则 5 是这一条的展开）。「直推 main、无人工评审、秒级部署」不是鲁莽，是换传感器：把慢而贵的人工评审换成快而自动的传感器组加快速回滚，赌环路延迟够低时小步快修比大步慢审稳定——赌注成立的前提仍是传感器组够硬。
3. **两个环真正的耦合点：反馈蒸馏成前馈。** 下游反复抓到的同类错误，要被编译成上游的一条新约束。只画双向箭头不做蒸馏，两个环就只是并排挂着，各自为战。

十二条在轴上的位置：

| 位置       | 原则                | 说明                                                                                                                                                                                                                                                                                                                  |
| ---------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前馈侧     | 3 · 7 · 8 · 9       | 塑造 agent 看到的输入。B 组整组在这一侧——上下文就是前馈通道本身；只盯仓库的清单会把它整个漏掉，原五条正是这么漏的                                                                                                                                                                                                     |
| 后馈侧     | 5 · 6 · 10          | 传感器与修正环：5 管传感器校准，6 是对产出总量的修正环，10 是给自己的判断配的小反馈环                                                                                                                                                                                                                                 |
| 双跨／蒸馏 | 1 · 2 · 4 · 11 · 12 | 1 把「卡住」编译成环境能力，是蒸馏的单步（刹车防的是蒸馏过量）；2 声明在前馈侧、执行在后馈侧——机械化就是给前馈约束配下游传感器；4 的「收尾写」把本会话的下游发现变成下会话的上游输入，是跨会话的蒸馏通道；11 复用别家蒸馏好的形状（常数不抄，因为它们蒸馏自别家的反馈环）；12 是反馈→前馈的编译器——读数进，机制缺陷出 |

本文档自身就是第三条推论的产物：伤疤是反馈，原则是蒸馏出来的前馈。

## A. 外环境

### 1. 设计环境，而非编写代码——但能力扩张要过判据

Agent 卡住时，诊断「缺什么能力」并把能力补进环境（工具、子 agent、脚手架），优先于替它写代码。刹车：一次卡住只授权补那一个能力，票原有的判据不动。没有这个刹车，原则 1 就是 scope 膨胀的许可证——「同意做这张票」会被悄悄读成「授权顺手长出三个新机制」。

### 2. 约束要么机械化，要么 fail-closed，不许停在文档

依赖方向、装配顺序这类能写成 linter／结构测试／断言的，就写成。写在文档里但没机械化的约束等于没有——本仓库的 AGENTS.md 实时生效需求写进了交接文档，照样在两张票之间丢掉；视图顺序曾经「今天对、只是碰巧对」，最后靠装配断言收口。

边界：机械化有成本前沿。有些约束够不着（权限规则只认命令前缀，管不住写文件的命令）；够不着的地方设计成默认拒绝，而不是宣称「要更严就配规则」开空头支票。

### 3. 仓库是唯一事实源；例外要有登记的路

Slack、外部文档、口头共识对 agent 等于不存在。推论：只能靠某个人（或某条会话记忆）才找得到的知识，已经处于丢失状态——它不需要再丢一次。允许 scratch 区存在，但每一块必须有一条从仓库或索引出发能走到它的路。

### 4. 会话必死；跨会话状态要有序列化协议

上下文死亡是常态，不是事故。五类状态都要落成仓库制品：**还剩什么、做到哪了、怎么跑、什么算完成、为什么这么定**。协议对称：每个会话以读它们开局、以写它们收尾。

「四大失败模式」全是这一条的现场——某个状态只活在单次会话里，会话一结束就死：

| 死掉的状态   | 失败现场                 | 制品                             | 会话协议                           |
| ------------ | ------------------------ | -------------------------------- | ---------------------------------- |
| 还剩什么     | 过早宣布项目完成         | 功能列表（结构化，来自输入规格） | 开局读，选单个功能开工             |
| 做到哪了     | 遗留 bug、未文档化的进度 | git 历史 + 进度文件              | 开局读进度与 git log；收尾提交两者 |
| 什么算完成   | 过早标记功能 passing     | 功能列表的状态字段               | 见下方订正                         |
| 怎么跑       | 每个会话重新摸索启动方式 | init.sh                          | 开局读                             |
| 为什么这么定 | 已定的决策被重新吵一遍   | ADR                              | 碰到相关决策时读；新决策落盘       |

第五行是原表没有的，由原则本身推出来：决策依据也是跨会话状态。原表只盯「做事」的状态，漏了「判断」的状态。

第三行的原对策（「自我验证所有功能，仅在仔细测试后才标记 passing」）违反原则 2——那是行为劝诫，不是机制，而且让被告自己当法官。订正：`passing` 只能由测试运行器写入，或门禁拒绝没有测试凭据的状态转换；默认值 not-passing（fail-closed）；再强一档是验证者与作者分离，另开一个只读制品的会话验收。

推论：制品要被每个会话真实使用。开局必读的文件不会静默腐烂——init.sh 坏了，下个会话开局就撞上；没人读的文档才会烂在原地。「开局读」这个协议同时是免费的陈旧传感器。

本仓库的取舍登记（2026-08-31 审查后补）：五类制品里「怎么跑」（README + package.json scripts）与「为什么这么定」（docs/adr/）入仓；「还剩什么」（learn/MISSION.md）、「做到哪了」（.scratch/\*/map.md）、「什么算完成」（.scratch/\*/issues/）是**有意的机器本地制品**——单机学习仓库，接受「换机器即丢失」，换来规划过程不进史。登记的路：`.gitignore` 的注释 → `.scratch/README.md` 的结构约定。这是取舍不是缺陷；重开条件：这个仓库有了第二台工作机器。

### 5. 可观测性先校准，再接给 Agent

给 agent 可度量的目标（「启动时间降到 800ms 以下」）只有在读数可信时才成立。三条判据，每条对应一次真实事故：

- 度量点放在最内层；绕过中间层的调用要自己上报。
- 观测面自身要有测试。一个 stub id 不唯一，守卫就假性哑掉，产出过一整份全错的根因分析。
- 每个指标接入前先确认它真的量到了东西。benchmark 里「动手前跑没跑检查」那栏是废数，因为八个环境里只有一个真的有检查可跑。

坏读数比没读数毒——它给出的是自信的错误结论。

### 6. 熵要有显式的偿还策略，策略与仓库形态匹配

「定期清理 AI slop」的诊断是对的，处方要拆开：自动化清扫只有在清理带确定性验收（测试、门禁）时才成立，否则是用 slop 清 slop。清扫也不是唯一策略——低生成吞吐量的仓库用 repair-on-touch（碰到才核才改）更便宜。真正的原则是：没写下偿还策略，默认策略就是「堆着」。

## B. 窗口内侧

原五条全在仓库一侧，但 harness 至少一半在上下文窗口内侧。下面三条是按实际花掉的工时补的。

### 7. 上下文是装配出来的视图，不是追加的日志

每一段进窗口的内容都要能回答：谁放的、排在哪、什么时候被换掉。排序轴用变化频率——稳定的在头部吃缓存，易变的沉底或走附言送增量。顺序要有装配断言守着：「今天的顺序对」和「必然对」是两回事，前者只是碰巧。

### 8. 删减按信息类别区分对待，不搞统一打分

压缩和摘要对不同类别的消息用不同策略；需要常驻的内容走显式注册表，不是靠「重要性」评分侥幸活下来。次序也是原则的一部分：先定信息模型，再堵个别漏洞——反过来做，堵一个漏一个。

### 9. 预算是剩余窗口的函数，不是常数

输出额度这类**管窗口账**的限制，按剩余空间算。拍下来的常数在窗口的另一头一定是错的：窗口空时它抠门，窗口满时它挥霍。

边界（2026-08-31 审查后补）：判据是「这个数记的是不是窗口账」。记窗口账的（输出额度、摘要额度）按剩余算；管内容形状的（单条工具结果的降级阈值这类字节属性）不随窗口变——pi 与 deer-flow 的同类阈值都是常数，照抄不自造。但常数必须是辩护过的：每个都要在注释里给出自己的理由，「今天的有效值」不算理由。

## C. 工作方式

前面九条本身也会烂。这三条是让它们持续为真的方法。

### 10. 先复现再定方案；推的环节做成便宜探针

写进注册表的判断被两条实测推翻过（窗口大小、completion 是否计入窗口）。A、B 里任何一条落地时的「我认为」，都值一个探针的价钱。

### 11. 抄成熟参考实现的机制，不抄它的常数

机制问题先找形状最接近的参考，整套抄形状；常数按本地条件自己定；抄不动的地方明说，不默默降级成自造轮子。

### 12. Benchmark 的产出是机制缺陷，不是分数

分数唯一的用途是指向「哪个机制缺了」。推论：配置一变，读数就跨不过那条线做差——配置要钉死并记账，否则连缺陷都指不准。
